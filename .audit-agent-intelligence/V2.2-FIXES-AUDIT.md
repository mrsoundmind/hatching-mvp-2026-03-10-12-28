## Phase A — Memory correctness · commit `a7957d5`

**Symptom.** A crude keyword extractor stored a *rejected* idea as an adopted "decision," duplicated
rows, and filed things like "6px tap target" as a "Project goal" because the word "target" matched. It
also ran twice per turn, and a second, better extractor was wired but crippled (no `generateFn`, and it
wrote float importance into an integer column so rows truncated to 0 and vanished).

**How it was fixed.**
- Retired the crude substring extractor and its two call sites in `server/routes/chat.ts`; the
  post-generation call's inputs (user message + saved response) are kept as the outcome signal.
- Made `server/ai/memoryExtractor.ts` the single writer: it now runs its LLM path (Groq, free), captures
  the **outcome** (accepted vs rejected) and stores a resolved fact, e.g. *"Team rejected storing
  everything in one JSON column, chose a normalized schema,"* not the raw @mention. Importance is emitted
  as an **integer 1 to 10** to match the column readers depend on (`memoryType ∈ decisions|key_points|
  context`, `importance >= 7` for shared memory). See the contract note at `memoryExtractor.ts:11,34-35`.
- Dedup at the storage layer so a repeated fact is not inserted twice.

**Files:** `server/ai/memoryExtractor.ts`, `server/routes/chat.ts`, `server/storage.ts`, `server/ai/openaiService.ts`.

**Verify:**
```bash
./node_modules/.bin/tsx --env-file=.env scripts/test-memory-extractor.ts   # expect 7/7
```
Live proof from the audit: a "rejected idea" turn stored the outcome, not an adopted decision; the
"call me Rohan" turn produced a clean "Saved a detail worth remembering" memory event.

## Phase B — First-person voice · commit `3d21b50`

**Symptom.** A hardcoded prompt example made every role open with "Good call from the PM side, let me
look at this from the ${role} angle," and role bios written in third person made agents refer to
themselves by name ("Alex thinks in RICE...").

**How it was fixed.**
- Removed the canned "Good call from the PM side" / "Alex was right..." example from the handoff section.
- Added an explicit first-person rule to the system prompt (rule #15, `server/ai/promptTemplate.ts:143`):
  *"You ARE ${agentName}. Always talk in the first person... Never refer to yourself by your own name or
  role in the third person... never open with a canned, templated phrase."*
- Reframed the HANDOFF and ROLE-EXPERTISE blocks to first person.

**Files:** `server/ai/promptTemplate.ts`, `server/ai/openaiService.ts`.

**Verify:**

## Phase C — Feedback that doesn't flatten · commit `9b35fef`

**Symptom.** Negative feedback nudged **every** trait toward a generic 0.5 center, collapsing all six
traits into a bland 0.45 to 0.55 band (blander, not smarter). Positive feedback could drift traits toward
the extremes (sycophancy). The interaction counter never accumulated in the feedback path.

**How it was fixed.**
- The feedback math now anchors **both** directions to each role's own baseline (resolved via
  `resolveBaseTraits` from `roleIntelligence`, `personalityEvolution.ts:90`), bounded by a band
  (`BAND = 0.15`): 👎 reverts gently toward the role baseline (no flatten to 0.5), 👍 is capped at
  baseline + 0.15 (no runaway sycophancy).
- The interaction counter now increments inside the feedback path and persists.

**Files:** `server/ai/personalityEvolution.ts`, `server/routes/messages.ts`.

**Verify:**
```bash
./node_modules/.bin/tsx scripts/test-personality-evolution.ts   # expect 17/17
```
Confirms 👎 does not flatten to 0.5, 👍 is capped at baseline+0.15, counter accumulates.

## Phase D — Real peer review with teeth + visibility · commits `6ec4973` (server) + `c2887fa` (visibility)

**Symptom.** "Peer review" was fully deterministic regex plus safety-score matching, the reviewing agent
never actually read the work, so it could not really reject bad output, and its result rendered as a blank
line in the Activity feed.

**How it was fixed.**
- New `server/autonomy/peerReview/llmJudge.ts`: a genuine LLM-as-judge. `runLlmJudge()` returns a real
  verdict (`approve|revise|reject` + severity + mustFix + confidence + reasoning); `aggregateVerdicts()`
  combines reviewers (worst confident verdict wins).
- Three safeguards, all in code: the judge runs on **Groq** (a different model family than the
  DeepSeek/Gemini writer, so it cannot favor its own family, self-preference mitigation); it is **blind to
  authorship**; and it is **fail-safe** (any failure returns null, which never blocks). Default on with an
  off switch (`FEATURE_PEER_REVIEW_JUDGE`).
- **Teeth:** a confident `reject` routes to the existing `pending_approval` block path, so genuinely bad
  autonomous work goes to the user instead of shipping. `revise` triggers a real bounded regeneration.
- **Visibility (`c2887fa`):** `peer_review_feedback` is a signal event (`shared/activityLabels.ts:74`) with
  verb labels, "Reviewed a teammate's work and approved it / asked for changes / sent it back"
  (`activityLabels.ts:161-163`), and reason + fixes on expand in `ActivityFeedItem.tsx`.

**Files:** `server/autonomy/peerReview/llmJudge.ts` (new), `peerReviewRunner.ts`,
`taskExecutionPipeline.ts`, `shared/activityLabels.ts`, `client/src/components/sidebar/ActivityFeedItem.tsx`.

**Verify:**
```bash

./node_modules/.bin/tsx --env-file=.env scripts/test-peer-review-integration.ts  # 9/9 (bad draft actually BLOCKED)
```

## PART 3 (the "start here" open item) — widen judge coverage · commit `f5682ab`

**Symptom.** Peer review only fired when `maxRisk >= peerReviewTrigger` (default **0.35**,
`server/autonomy/config/policies.ts:24`), so any task scoring below 0.35 shipped with **no review at
all**, which is most ordinary work. "Teeth exist" was true only when the judge ran, and it ran rarely.

**How it was fixed.**
- New `shouldReviewAutonomousOutput()` (`taskExecutionPipeline.ts:72`) broadens the gate: review fires on
  (1) mid/high risk, (2) outward-facing/factual content regardless of risk (regex `OUTWARD_OR_FACTUAL`),
  or (3) any substantive deliverable (`>= PEER_REVIEW_MIN_CHARS`, default 180, `taskExecutionPipeline.ts:68,81`).
  Only trivial acks skip. Wired at **both** call sites (`:408` and `:635`), both passing `enableLlmJudge:true`.
- The linchpin: the legacy risk-only veto inside `runPeerReview` is bypassed via `forcedByJudge`
  (`peerReviewRunner.ts:165-166,168`) with reason `coverage_review`, so a low-risk-but-substantive task the
  pipeline elected to review is no longer silently vetoed downstream (no inert-fix trap).

**Files:** `server/autonomy/execution/taskExecutionPipeline.ts`, `server/autonomy/peerReview/peerReviewRunner.ts`.

**Verify:**
```bash
./node_modules/.bin/tsx --env-file=.env scripts/test-review-coverage.ts            # 5/5 (factual/outward/substantive → review; trivial → skip)
./node_modules/.bin/tsx --env-file=.env scripts/test-peer-review-integration.ts    # 9/9 incl. "low-risk draft: judge STILL ran"
```
Live corroboration in the audit: verdict-bearing events went 8 → 11 after ordinary tasks; the newest 3
carry confidence in the payload (this also upgraded T2 to live-verified).

## PART 4 (minor quirks, both closed) — review↔run lineage · commit `eb228ca`

**Symptom 1.** A review verdict could not be joined back to the task/run it reviewed.
**Symptom 2 (turned out to be a measurement artifact).** Timestamps looked ~9h off.

**How it was fixed.**
- Review events now stamp `taskId` + `runTraceId` into the **payload**
  (`peerReviewRunner.ts:115-116,194-195,314-315`), while the per-event grouping `trace_id` stays unique,
  so a verdict joins to its run **and** keeps its own feed row (T3 preserved). The join key matches by
  construction: the run is created with `traceId`, and the review stamps that same value as `runTraceId`.
- The "9h skew" was not a column bug: with events previously unjoinable, the comparison had paired a
  verdict against an unrelated run. Columns are `timestamptz`/UTC and were correct. Joined to the right
  run, the pair is ~1.3s apart.

**Files:** `server/autonomy/peerReview/peerReviewRunner.ts`, `server/autonomy/execution/taskExecutionPipeline.ts`.

**Verify:**
```bash
./node_modules/.bin/tsx --env-file=.env scripts/verify-review-lineage-live.ts   # 6/6 (carries taskId + runTraceId, own trace_id, joins to run, timestamps seconds apart)
```
